# ADR-004: Adoção de Monorepo

- **Status:** Aceita
- **Data:** 01/11/2026

## Contexto

O projeto será composto por diferentes partes, incluindo o backend, responsável pelas regras de negócio e exposição da API REST, o frontend, responsável pela interface com o usuário, e a documentação técnica e funcional.

É necessário definir como esses componentes serão organizados e versionados, considerando que fazem parte de um mesmo sistema e serão desenvolvidos e mantidos dentro do mesmo projeto.

Manter os componentes em repositórios separados poderia exigir um gerenciamento adicional de versões e dependências entre eles, enquanto um repositório único permite centralizar o desenvolvimento e o versionamento.

## Alternativas Consideradas

- **Monorepo:** manter frontend, backend e documentação em um único repositório Git, organizados em diretórios independentes.
- **Multirepo:** manter cada componente do sistema em um repositório Git separado, permitindo versionamento e gerenciamento independentes.

## Decisão

Será adotada a abordagem de **Monorepo**, mantendo todos os componentes do sistema em um único repositório Git.

A estrutura inicial será organizada da seguinte maneira:

```text
project/
├── backend/
├── frontend/
└── documentation/
```

Cada diretório será responsável por armazenar seu respectivo conteúdo:

- **backend/**: código-fonte da API REST e implementação das regras de negócio.
- **frontend/**: código-fonte da aplicação de interface com o usuário.
- **documentation/**: documentação funcional e técnica do projeto, incluindo requisitos, arquitetura, diagramas e decisões arquiteturais.

Cada componente poderá manter suas próprias configurações, dependências, ferramentas de desenvolvimento e processos de execução, mesmo compartilhando o mesmo repositório.

## Consequências

### Positivas

- **Versionamento centralizado:** todos os componentes do sistema terão seu histórico de alterações mantido em um único repositório.
- **Rastreabilidade:** facilita acompanhar alterações relacionadas entre frontend, backend e documentação.
- **Organização:** mantém os componentes centralizados, mas separados por diretórios e responsabilidades.
- **Facilidade de desenvolvimento:** permite realizar alterações coordenadas em diferentes partes do sistema dentro de um mesmo commit.
- **Documentação próxima ao código:** facilita manter os documentos atualizados e centraluzados conforme a implementação evolui.
- **Simplificação do gerenciamento:** evita a necessidade de administrar múltiplos repositórios para os componentes do projeto.

### Negativas

- **Histórico compartilhado:** todos os componentes compartilham o mesmo histórico de commits.
- **Gerenciamento de permissões:** o acesso ao repositório é compartilhado, dificultando permissões independentes por componente.
- **Crescimento do repositório:** conforme o projeto evolui, o repositório poderá acumular arquivos, dependências e históricos maiores.
- **Necessidade de organização:** exige uma estrutura de diretórios consistente para evitar misturar responsabilidades entre os componentes.
