# ADR-005: Adoção de API REST para Comunicação entre Frontend e Backend

- **Status:** Aceita
- **Data:** 01/11/2026

## Contexto

O sistema será desenvolvido com frontend e backend separados, sendo o backend responsável pelas regras de negócio, processamento das operações e persistência dos dados, enquanto o frontend será responsável pela interface e interação com o usuário.

É necessário estabelecer um padrão de comunicação entre essas aplicações que permita a troca de informações e a execução das funcionalidades disponibilizadas pelo backend.

Considerando a separação entre frontend e backend, é importante adotar uma abordagem padronizada, independente das tecnologias utilizadas em cada camada e que permita evoluir os componentes separadamente.

## Alternativas Consideradas

- **API REST:** utilizar requisições HTTP seguindo os princípios e convenções REST, com recursos identificados por endpoints e operações representadas por métodos HTTP.
- **GraphQL:** utilizar uma linguagem de consulta para permitir que o cliente solicite especificamente os dados necessários, por meio de um endpoint geralmente centralizado.

## Decisão

Será adotada uma **API REST (Representational State Transfer)** como padrão de comunicação entre frontend e backend.

O backend disponibilizará endpoints HTTP para expor os recursos e funcionalidades do sistema, permitindo que o frontend realize operações por meio de requisições HTTP.

A API seguirá as convenções do protocolo HTTP, considerando:

- **Métodos HTTP:** utilização de métodos como GET, POST, PUT, PATCH e DELETE, conforme a finalidade de cada operação.
- **Códigos de status HTTP:** utilização de códigos apropriados para representar os resultados das requisições.
- **Formato de dados:** utilização de JSON para troca de informações entre cliente e servidor.
- **Organização dos endpoints:** utilização de recursos e rotas que representem os conceitos e funcionalidades disponibilizados pelo sistema.
- **Documentação:** disponibilização da documentação dos endpoints por meio de OpenAPI/Swagger.

A comunicação será realizada por HTTP, utilizando HTTPS nos ambientes de implantação para proteger os dados transmitidos.

## Consequências

### Positivas

- **Padronização:** utilização de convenções amplamente adotadas para comunicação entre aplicações.
- **Independência tecnológica:** permite que frontend e backend utilizem tecnologias diferentes, desde que respeitem o contrato da API.
- **Separação de responsabilidades:** o frontend consome as funcionalidades disponibilizadas pelo backend sem precisar conhecer suas implementações internas.
- **Facilidade de integração:** permite que outras aplicações ou clientes consumam os mesmos recursos futuramente.
- **Documentação:** facilita a descrição, consulta e utilização dos endpoints por meio de ferramentas como OpenAPI/Swagger.
- **Manutenção:** permite evoluir frontend e backend separadamente, desde que os contratos de comunicação sejam preservados.

### Negativas

- **Comunicação via HTTP:** as operações dependem de requisições e respostas entre cliente e servidor, introduzindo latência de comunicação.
- **Contrato entre aplicações:** alterações nos endpoints, formatos de dados ou comportamentos podem exigir ajustes no frontend e em outros consumidores.
- **Gerenciamento de erros:** é necessário definir padrões consistentes para representar erros e resultados das requisições.
