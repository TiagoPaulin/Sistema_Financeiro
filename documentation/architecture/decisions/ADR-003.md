# ADR-003: Comunicação entre Módulos por meio de APIs Públicas Internas

- **Status:** Aceita
- **Data:** 01/11/2026

## Contexto

O backend será desenvolvido seguindo uma arquitetura de Monólito Modular, na qual cada módulo será responsável por uma área funcional específica do sistema.

Apesar de possuírem responsabilidades distintas, os módulos precisarão interagir para executar determinados casos de uso. Por exemplo, uma operação de movimentação financeira poderá precisar consultar ou atualizar informações pertencentes ao módulo de contas.

Permitir que um módulo acesse diretamente os componentes internos de outro, como Repositories, Entities ou classes de implementação dos Services, criaria dependências entre detalhes internos de implementação.

Esse tipo de dependência aumenta o acoplamento entre os módulos, dificulta alterações futuras e compromete o isolamento que a arquitetura modular busca proporcionar.

Diante disso, é necessário estabelecer uma forma padronizada de comunicação que permita a interação entre os módulos sem expor suas implementações internas.

## Alternativas Consideradas

- **Acesso direto aos componentes internos:** permitir que os módulos utilizem diretamente Services, Repositories e Entities de outros módulos. Embora seja uma abordagem simples inicialmente, aumenta o acoplamento e reduz o encapsulamento.
- **APIs públicas internas:** cada módulo disponibiliza contratos públicos com as funcionalidades que podem ser utilizadas pelos demais módulos, mantendo suas implementações internas encapsuladas.

## Decisão

A comunicação entre os módulos será realizada prioritariamente por meio de **APIs públicas internas (Public APIs)**.

Cada módulo poderá disponibilizar um pacote `api/`, contendo interfaces ou classes responsáveis por expor as funcionalidades que outros módulos precisam utilizar.

Os módulos consumidores deverão depender exclusivamente desses contratos públicos, sem acessar diretamente os componentes internos do módulo responsável pela funcionalidade.

Por exemplo, caso o módulo de movimentações precise realizar um débito ou crédito em uma conta, deverá utilizar uma operação disponibilizada pela API pública do módulo de contas.

A implementação dessa funcionalidade permanecerá encapsulada no próprio módulo de contas.

As APIs públicas deverão expor somente as operações necessárias para a comunicação entre módulos, evitando disponibilizar detalhes internos de implementação.

## Consequências

### Positivas

- **Redução do acoplamento:** os módulos dependem de contratos públicos, e não de classes ou implementações internas de outros módulos.
- **Encapsulamento:** cada módulo mantém controle sobre suas regras de negócio e detalhes de implementação.
- **Flexibilidade de manutenção:** alterações internas poderão ser realizadas sem exigir modificações nos módulos consumidores, desde que os contratos públicos sejam preservados.
- **Clareza nas dependências:** os pontos de comunicação entre os módulos ficam explícitos, facilitando a compreensão da arquitetura.
- **Maior testabilidade:** permite testar os módulos consumidores utilizando implementações simuladas dos contratos públicos.

### Negativas

- **Manutenção de contratos:** alterações nas APIs públicas podem exigir ajustes nos módulos que dependem delas.
- **Estrutura adicional:** a criação de interfaces e classes públicas pode aumentar a quantidade de componentes do projeto.

## Diretrizes de Implementação

Para preservar a decisão arquitetural, deverão ser observadas as seguintes diretrizes:

- Módulos consumidores deverão acessar funcionalidades externas somente por meio das APIs públicas disponibilizadas pelos módulos responsáveis.
- Repositories, Entities JPA e implementações internas de Services não deverão ser acessados diretamente por outros módulos.
- As APIs públicas deverão expor somente as operações necessárias, evitando disponibilizar detalhes internos.
- A criação de contratos públicos deverá ocorrer quando houver necessidade real de comunicação entre módulos, evitando abstrações desnecessárias.
