# ADR-007 — Adoção do Flyway para Gerenciamento de Migrações do Banco de Dados

- **Status:** Aceita
- **Data:** 02/11/2026

## Contexto

O projeto utiliza PostgreSQL como sistema gerenciador de banco de dados e necessita de uma estratégia para controlar a evolução de sua estrutura ao longo do desenvolvimento.

Como o sistema terá diferentes entidades e relacionamentos, alterações no schema serão necessárias conforme novas funcionalidades forem implementadas.

É necessário manter essas alterações versionadas e rastreáveis, garantindo que a estrutura do banco possa ser reproduzida em diferentes ambientes.

## Alternativas Consideradas

- **Flyway:** Ferramenta de gerenciamento de migrações que permite versionar alterações na estrutura do banco por meio de scripts SQL.
- **Gerenciamento manual:** Realizar alterações diretamente no banco de dados, sem uma ferramenta específica de controle de migrações.

## Decisão

Foi decidido utilizar o **Flyway** para gerenciar e versionar as migrações do banco de dados.

As alterações na estrutura do banco serão definidas manualmente por meio de scripts SQL versionados, armazenados no repositório junto ao backend.

Os scripts seguirão o padrão de nomenclatura do Flyway, utilizando versões sequenciais, como:

```text
src/main/resources/db/migration/
├── V1__create_users_table.sql
├── V2__create_accounts_table.sql
├── V3__create_categories_table.sql
└── V4__create_transactions_table.sql
```

O Flyway será responsável por identificar e executar as migrações pendentes, mantendo um histórico das alterações realizadas por meio da tabela `flyway_schema_history`.

O Hibernate será utilizado para o mapeamento objeto-relacional (ORM), sem responsabilidade de criar ou modificar automaticamente a estrutura do banco de dados.

Para isso, será utilizada a configuração:

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Essa configuração permite que o Hibernate valide se o mapeamento das entidades corresponde à estrutura existente no banco, sem realizar alterações automáticas no schema.

## Consequências

### Positivas

- Mantém as alterações do banco de dados versionadas junto ao código-fonte.
- Permite rastrear o histórico de evolução da estrutura do banco.
- Facilita a reprodução da estrutura do banco em diferentes ambientes.
- Garante maior controle sobre a criação e alteração de tabelas, colunas, relacionamentos e restrições.
- Permite aprofundar os conhecimentos em gerenciamento de migrações utilizando uma ferramenta específica.
- Separa a responsabilidade de evolução do schema da responsabilidade de mapeamento objeto-relacional do Hibernate.

### Negativas

- Será necessário criar e manter scripts SQL para cada alteração na estrutura do banco.
- Será necessário manter os scripts de migração compatíveis com a evolução das entidades e dos requisitos do sistema.

## Observações

As migrações serão executadas pelo Flyway durante a inicialização da aplicação, conforme a configuração do ambiente.

O Hibernate permanecerá responsável pelo mapeamento entre as entidades Java e as tabelas do PostgreSQL, utilizando a validação do schema para identificar possíveis divergências entre o modelo de persistência e a estrutura do banco de dados.
